# Intent: 채팅으로 어드민을 만드는 플랫폼 (admin-ui)

- **Author:** sangwookpark
- **Status:** draft
- **Date:** 2026-09-11
- **Background:** 토스 TOI("AI 시대 어드민", 2026-08-25 웨비나 · toss.tech/article/52885) 비판 분석과 실측 결과

## Problem

어드민이 필요할 때마다 같은 일을 반복한다. 프로젝트 스캐폴딩, 의존성, 빌드, 인증, 배포, API 연동을 매번 새로 만든다.
어드민에는 마스킹, 조회 사유, 다운로드 암호화, 감사 로그 같은 규칙이 붙는데, 어드민을 제각각 만들면 이 규칙이 고르게 적용되지 않는다.
FE 인력이 없는 팀은 어드민을 못 만들거나, 서버 개발자가 따로 만들어 쓴다. 이렇게 만든 어드민은 누가 소유하는지, 어떤 API를 쓰는지 추적되지 않는다.

## Proposed Outcome

서버 개발자가 API를 등록하고 채팅으로 요구사항을 말하면, 몇 분 안에 동작하는 어드민 화면이 나온다.

- **데이터 정책은 AI가 아니라 플랫폼이 보장한다.** 생성된 UI는 플랫폼 프록시만 호출하고, 권한·마스킹·암호화·감사는 프록시에서 강제한다.
- **프리뷰는 브라우저 안에서 빠르게 돈다.** 의존성 준비는 편집/프리뷰 경로에서 분리한다. 앱 코드만 브라우저에서 번들한다.
- **실행까지 성공한 최신 revision만 화면에 반영한다.** 실패하면 마지막 정상 화면을 유지한다.
- **라이브 어드민은 계속 관리된다.** 어떤 앱이 어떤 API 스키마 버전과 패키지를 쓰는지 역추적할 수 있다.

## Affected Users and Systems

**Users**
- 서버 개발자: 주 사용자. API를 등록하고 어드민을 만든다.
- 디자이너, PO: 문구나 레이아웃 같은 가벼운 수정을 한다.
- FE 개발자, API owner: 리뷰어. PR로 복잡한 로직과 데이터 권한을 검토한다.
- 보안·컴플라이언스 담당: 데이터 정책을 정의한다.

**Systems**
- 채팅·에이전트 서버: 코드를 생성하고, 이벤트 스트림과 역질문을 처리한다.
- API 레지스트리: 등록 API와 스키마 버전을 관리한다.
- 정책 프록시: 권한, 마스킹, 암호화, 감사 로그를 처리한다.
- 의존성 빌드 워커: 사내 레지스트리에서 설치하고 빌드해 immutable 산출물과 manifest를 만든다.
- 객체 저장소와 CDN: 소스와 의존성 산출물을 저장한다.
- 브라우저 프리뷰 런타임: 메모리 VFS, 번들러, 격리된 iframe으로 구성한다.
- Git 저장소와 PR 리뷰, 사내 SSO, 사내 디자인시스템

## Constraints

- **자격증명:** 사내 레지스트리 토큰과 upstream 서비스 자격증명은 브라우저에 노출하지 않는다.
- **권한:** 쓰기 요청마다 서버가 user, project, 등록 API, action, resource, env를 검증한다. UI에서 버튼을 숨기는 것은 권한 근거가 아니다.
- **프리뷰 side effect:** 프리뷰는 기본적으로 테스트 데이터나 read-only로 실행한다. "화면 롤백"이 API 쓰기의 롤백을 뜻하지 않는다.
- **캐시 키:** 캐시 키에 lockfile뿐 아니라 빌드 도구·설정 지문을 포함한다. 산출물 자체의 digest는 따로 기록하고 검증한다.
- **싱글톤:** React처럼 인스턴스가 하나여야 하는 패키지는 import map의 단일 URL과 peer external 규칙으로 보장한다. 이 규칙은 검증 대상이다.
- **동시성:** 소스 저장은 baseRevision CAS로 보호한다. 늦게 끝난 이전 빌드는 화면에 반영하지 않는다.
- **격리:** 번들러를 고를 때 COOP/COEP 격리 요구와 iframe 임베드 조건을 함께 따진다. 예를 들어 Rolldown browser 1.2.8은 격리 없이는 동작하지 않았다.
- **파일 삭제:** 미릴리즈 앱을 무통보로 영구 삭제하지 않는다. 알림 → 보존 기간 → 복구 가능한 archive 순서로 정리한다.

## Open Questions

1. 1차 범위는 브라우저 FE 프리뷰까지인가, SSR과 통합테스트용 원격 샌드박스까지인가?
2. 의존성 캐시 단위는 무엇인가? 조합 단위(TOI 방식), 패키지 단위 ESM + resolution manifest, 둘을 섞은 방식 중 무엇으로 할지는 조합 분포와 적중률을 측정한 뒤 정한다.
3. 번들러는 esbuild-wasm으로 할지, 번들 없는 방식(Oxc + blob URL + import map)으로 할지? 첫 화면은 번들 없는 방식이 빨랐지만 수정 반영은 동률이었다. 순환 import와 URL 전파 비용도 있다.
4. 패키지 매니저는 무엇으로 하는가? 조직 표준을 따른다. 실측으로는 필연적인 선택지가 없었다.
5. API 스키마는 어떤 형식인가(OpenAPI 버전 등)? 등록 경로와 스키마 변경 시 영향 분석은 어떻게 할까?
6. 채팅 스트림은 SSE와 WebSocket 중 무엇으로 할까? 이벤트 스키마(seq, question/answer, revision_ready, canceled)는 어떻게 정할까?
7. 성공 지표는 무엇인가? 첫 화면 p50/p95, 캐시 hit/miss, 라이브 전환율, 정책 위반 0건 등을 구분해서 정의해야 한다.
8. 생성 코드를 누가 리뷰하는가? CODEOWNERS와 필수 승인자를 어떻게 정할까?
