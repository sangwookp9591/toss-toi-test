토스 TOI 해부: 채팅으로 어드민을 만드는 플랫폼은 어떻게 빨라졌나

토스 FE 웨비나(2026-08-25)의 ‘AI 시대 어드민’ 세션을 1차 자료와 직접 실측으로 뜯어본 기록입니다. 핵심 질문은 다섯 가지입니다. 무엇을 놓쳤나, 더 잘 만들 수 있었나, 왜 esbuild-wasm이고 왜 yarn인가, 그리고 채팅 UI는 Backend와 어떻게 통신했나.

분석 Claude Opus · 실측·조사 Codex Astra (high) · 상호 비평 2라운드 1차 자료 toss.tech/article/52885 · 전체 웨비나 · 편집본
확인1차 자료·실측 추정근거에서 도출 unverifiable공개 자료로 확정 불가

한 줄 결론

  1. 47초 → 1.3초는 esbuild 덕이 아닙니다. 의존성 준비를 편집·프리뷰 경로에서 떼어낸 아키텍처 전체의 결과입니다. 추정
  2. esbuild-wasm도 yarn도 필연은 아니었습니다. 둘 다 합리적인 선택이었고, 교체 우선순위는 낮습니다. 확인
  3. 가장 큰 빈칸은 엔진이 아니라 운영입니다. 불완전한 캐시 키, 되돌릴 수 없는 프리뷰 side effect, 라이브 약 120개 앱의 수명주기 관리가 남아 있습니다.

왜 esbuild-wasm이었나

TSX 변환, import 연결, 가상 파일시스템(VFS) 플러그인, 증분 빌드를 wasm 하나로 해결하고, 격리 헤더 없이도 브라우저에서 돕니다. 필수라서가 아니라 모듈 연결기(linker)를 직접 만들 부담을 덜어 주는 선택이었습니다.

번들러 없이도 됐을까: 번들 없는 방식 실측

파일마다 Oxc로 변환하고, 상대 import를 blob URL로 바꾸고, 외부 의존성은 import map으로 연결하는 방식을 esbuild 번들과 비교했습니다. 입력은 React TSX 4개 파일에 데이터 100행입니다.

지표 (Chrome, ms)번들 없는 방식 (Oxc)esbuild 번들
준비 포함 첫 화면132.3299.9

첫 화면은 번들 없는 방식이 빨랐지만, 사용자가 체감하는 수정 반영은 동률입니다. 번들 없는 방식에는 순환 import 거부, 참조하는 파일로 번지는 URL 교체, 2단계 source map 추적이라는 구현 비용이 남습니다.

Rolldown (Vite 8 코어)

@rolldown/browser 1.2.8은 COOP/COEP 격리가 없으면 3/3 실패했습니다(SharedArrayBuffer transfer requires crossOriginIsolated). 격리하면 동작하고, 프리뷰 iframe도 COEP+CORP와 allow="cross-origin-isolated"를 주면 임베드됩니다. 따라서 채택할 때의 비용은 속도가 아니라 격리 정책입니다. 확인

처음에 보인 ‘브라우저 177ms 대 Node 55ms’ 차이는 측정 조건이 달랐기 때문이었습니다. Node 쪽만 예열이 들어가 있었고, 조건을 맞추니 둘 다 약 50ms였습니다.

왜 하필 yarn이었나

같은 의존성 세트로 패키지 매니저 5종을 비교했습니다. lockfile은 모두 3회 생성해도 해시가 같았고, frozen 설치 뒤에도 바뀌지 않았습니다. 결정성은 yarn만의 장점이 아닙니다. 확인

놓친 부분

공개된 구현(4계층 VFS, Worker 실행, 실패 시 정상 화면 유지, Git PR 리뷰, MCP/GitOps)은 누락으로 보지 않았습니다.

Package Set Hash는 빌드 산출물의 이름이 아닙니다

공개된 규칙 sha256({정렬된 엔트리, sha256(lockfile)}).slice(0,16)을 재현해 입력을 하나씩 바꿔 봤습니다. 확인

바꾼 것키변경
기준165bdc14048005a3—
lockfile 공백만e595d8a19df88518바뀜 (의미 없는 캐시 miss)
빌드 도구 버전만165bdc14048005a3그대로 (위험)
빌드 설정·NODE_ENV만165bdc14048005a3그대로, minify만 달라도 산출물 해시는 달라짐

토스가 별도의 네임스페이스로 이를 보완하는지는 unverifiable입니다.

그 밖의 빈칸

  • ‘트랜잭션 커밋’은 화면만 되돌립니다. 프리뷰가 실행 중에 보낸 쓰기 요청은 되돌릴 수 없습니다.
  • 1.3초의 정의가 없습니다. cold인지 warm인지, 캐시 hit인지 miss인지, p95는 얼마인지가 빠져 있습니다.
  • 수명주기: 미릴리즈 약 300개는 ‘지금은 회수하지 않고 나중에 정리할 계획’이라고 Q&A에서 답했습니다. React·디자인시스템 업그레이드와 API 변경 시 영향받는 앱을 역추적하는 방법은 unverifiable입니다.
  • 실행 격리: 프록시는 브라우저로 가는 데이터를 줄일 수 있지만, 이미 화면에 표시된 데이터가 외부로 나가는 것은 막지 못합니다. CSP, 프리뷰 origin, sandbox 설정은 공개되지 않았습니다.

더 잘 만들 수 있었나: 합의된 우선순위

P0

역인덱스: 앱 ↔ owner ↔ 라이브 릴리즈 ↔ 소스·manifest 해시 ↔ 등록 API 스키마 버전을 잇습니다. API 스키마가 바뀌면 영향받는 앱 목록과 호환성 검사가 나오게 합니다.

P0

캐시 키 보강: lockfile 원본 해시에 빌드 도구·설정 지문을 더하고, 산출물 자체의 해시도 따로 기록합니다. lockfile을 의미 단위로 정규화하는 건 불필요한 miss가 많다는 데이터가 나온 뒤에 합니다.

P1

안전한 업그레이드와 정리: codemod → 타입·계약·smoke 검증 → owner 리뷰 → 단계 배포 순서로 업그레이드합니다. 미릴리즈 앱은 알림 → 보존 기간 → 복구 가능한 archive 순으로 정리합니다.

P2

패키지 단위 ESM 캐시: 승인된 패키지 카탈로그 범위에서 먼저 실험합니다. 실측에서 React와 QueryClient가 하나로 공유됐고(3/3), React를 중복 포함한 대조군은 3/3 실패했습니다. 다만 CJS 변환 계층과 external 규칙을 정확히 맞추는 비용이 있습니다.

엔진 교체(Rolldown, 번들 없는 방식, pnpm)는 수정 반영 속도가 동률이라 운영 과제보다 뒤에 둡니다.

채팅으로 어드민을 만들 때 Backend 통신

확인 공개된 골격

  • API를 먼저 등록하고, 요청·응답 스키마로 코드를 생성
  • 생성된 UI의 데이터 호출은 TOI 서버 프록시 경유(로그, 마스킹, 조회 사유, 다운로드 암호화)
  • 코드는 S3, 편집 중 VFS는 메모리
  • 의존성은 yarn → Vite → import map → S3
  • 레지스트리 자격증명은 브라우저에 노출하지 않음

unverifiable 공개되지 않음

  • SSE인지 WebSocket인지, 이벤트 스키마
  • 에이전트 모델·SDK
  • 스키마 규격(OpenAPI 버전)
  • SSO, 토큰, RBAC 구현
  • 배포 구조와 승인 강제 여부

공개 사실과 모순되지 않는 설계 제안

POST /generations {projectId, prompt, baseRevision, requestId}
GET  /generations/{id}/events    seq 단조 증가 · 재연결 replay
     text · question(+answer) · file · revision_ready{sourceDigest, manifestDigest}
     failed · canceled
requested→staging→revision_ready→deps_ready→built→runtime_verified→committed

서버 저장은 baseRevision CAS로 충돌을 막고, 화면 교체는 실행까지 검증됐고 여전히 ‘최신 의도 revision’인 후보일 때만 합니다. 둘은 서로를 대신하지 못합니다.

완료 순서판정
r10 요청 → r11 요청 → r11 성공 → r10 성공r11만 커밋, r10은 늦게 왔으므로 폐기
r9 정상 → r10·r11 요청 → r11 실패 → r10 성공r9 유지, r10을 자동 커밋하지 않음
같은 r11, manifest 변경 후 이전 attempt 성공거부 (attempt·manifest 불일치)
취소 뒤 늦은 complete 도착거부 (canceled 종결 상태)

생성 UI → 프록시 구간에서는 user·project·등록 API·action·resource·env 권한을 요청마다 서버가 검증합니다. 버튼을 숨기는 것은 권한 근거가 아닙니다.

남은 이견과 한계

  • ‘URL이 하나면 싱글톤’은 조건부입니다. 같은 실행 환경(realm), 명시된 peer, 숨은 중복 없음, 공유 객체 주입이 전제될 때만 성립합니다.
  • lockfile 정규화는 나중에 합니다. 원본 해시에 빌드 지문을 더하는 게 먼저이고, 과하게 무효화되는 쪽이 안전합니다.
  • 측정 범위: Apple M4 한 대, 작은 fixture, 3회 중앙값입니다. 큰 그래프, CSS·asset, 사내 레지스트리, WAN p95, 동시 빌드 경합은 측정하지 못했습니다. 어느 수치도 토스의 1.3초를 독립적으로 재현한 것이 아닙니다.
이 분석을 바탕으로 admin-ui 저장소에 intent/INTENT.md를 작성했습니다. 채팅으로 어드민을 만드는 플랫폼의 proto-spec이고, 상태는 draft입니다. 토스와 무관한 독립 분석입니다. 수치는 공개 자료와 로컬 PoC에서 나왔습니다.
